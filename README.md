# Согласование и выполнение заявок на продление

Тестовое задание Fullstack. Сотрудник создаёт заявку на продление ресурса, другой сотрудник её
согласует, после чего приложение отправляет операцию внешнему провайдеру и переживает
неопределённый ответ (HTTP 503 после фактического выполнения) без повторного продления.

- **Бэкенд:** Node.js, NestJS 11, Prisma 6, PostgreSQL 17
- **Фронтенд:** React 19, TypeScript, Vite 7
- **Фоновый обработчик:** работает внутри процесса бэкенда, состояние хранит только в базе

## Версии инструментов

| Инструмент | Версия |
|---|---|
| Node.js | 22 или новее (проверено на 25.2.1) |
| npm | 10 или новее |
| Docker + Docker Compose | любая актуальная (нужна только для PostgreSQL) |
| Python | 3.x (только для имитатора провайдера) |

## Запуск

Нужны четыре терминала. Все команды — от корня репозитория.

**1. База данных** (PostgreSQL в Docker, порт `5433`):

```bash
docker compose up -d --wait
```

**2. Имитатор провайдера** (порт `8091`):

```bash
python provider_simulator.py
```

**3. Бэкенд и фоновый обработчик** (порт `4000`; обработчик запускается вместе с приложением):

```bash
cd backend
cp .env.example .env        # в Windows: copy .env.example .env
npm install
npm run db:migrate          # миграции
npm run db:seed             # начальные данные (полностью пересоздаёт данные)
npm run build
npm start
```

**4. Фронтенд** (порт `5173`):

```bash
cd frontend
npm install
npm run dev
```

Откройте <http://127.0.0.1:5173>.

Вернуть базу к начальному состоянию: `npm run db:seed` в папке `backend`
(имитатор при этом тоже нужно перезапустить, чтобы его счётчики обнулились).

## Как воспроизвести сценарий с перезапуском

### Автоматически

Скрипт запускает бэкенд отдельным процессом, доводит заявку до ответа 503, **жёстко останавливает
процесс**, запускает его снова и проверяет результат по базе и по имитатору.

```bash
# база запущена; имитатор запущен ЗАНОВО (без операций); бэкенд на порту 4000 можно не останавливать
cd backend
npm run build
node scripts/acceptance.mjs
```

Скрипт пересоздаёт начальные данные и печатает список проверок раздела «Приёмка» с результатом каждой.

### Вручную через интерфейс

1. Поставьте в `backend/.env` `PROVIDER_RETRY_DELAY_MS=30000`, чтобы было 30 секунд на остановку.
2. Перезапустите имитатор, выполните `npm run db:seed`, запустите бэкенд.
3. Войдите как **Инициатор Alpha**, создайте заявку на «Хранилище A». Срок остаётся 01.03.2027.
4. Выйдите, войдите как **Согласующий Alpha**, откройте заявку и нажмите «Одобрить».
5. В истории заявки появится запись «Попытка 1 из 3: подтверждение не получено (HTTP 503)».
   В этот момент остановите бэкенд (`Ctrl+C` или закройте процесс).
6. Проверьте имитатор: операция уже существует.
   `curl "http://127.0.0.1:8091/stats?resource_id=res-a-01"` → `operation_count: 1`.
7. Запустите бэкенд снова (`npm start`). Обработчик найдёт задачу в базе, запросит результат по
   тому же ключу и завершит заявку.
8. В интерфейсе: заявка «Завершена», срок ресурса **31.03.2027**.

### Какой ключ операции использовать

Ключ идемпотентности — это **id заявки** (UUID). Он показан в окне заявки в поле «Ключ операции»
и приходит в API в поле `operationKey`.

```bash
curl "http://127.0.0.1:8091/renewals/<ключ операции>"        # started_count: 1
curl "http://127.0.0.1:8091/stats?resource_id=res-a-01"      # operation_count: 1
curl "http://127.0.0.1:8091/stats?resource_id=res-a-02"      # operation_count: 0
```

## Модель состояний

```
                       отклонить
  На согласовании ───────────────────▶ Отклонена
   (pending)                           (rejected)
        │
        │ одобрить (не автор заявки; снимок ресурса актуален)
        ▼
    Выполняется ──── провайдер подтвердил ───▶ Завершена
    (executing)                                (completed)
        │   ▲
        │   │ повторить (согласующий, тот же ключ)
        ▼   │
   Требует внимания
   (needs_attention)
```

- Активные состояния (блокируют новую заявку на ресурс): `pending`, `executing`, `needs_attention`.
- Любой другой переход возвращает **409**.
- Каждая смена состояния пишется в `request_events`: автор (или «Система»), время, откуда и куда,
  пояснение. Туда же попадают неудачные попытки отправки.
- При создании заявки фиксируется снимок ресурса: сумма, валюта, прежний срок и новый срок
  (прежний + 30 календарных дней).

## Обработка неопределённого ответа и восстановление

Задача отправки — строка в таблице `dispatch_jobs`. Обработчик выполняет её так:

1. **GET `/renewals/{ключ}`** — возможно, операция уже есть у провайдера (после 503 или после
   перезапуска приложения). GET ничего не создаёт и попыткой не считается.
2. Если операции нет и попыток меньше трёх — **POST `/renewals`** с тем же ключом и телом.
   Номер попытки записывается в базу *до* отправки.
3. Исход:
   - провайдер вернул операцию `completed` → результат, статус заявки и новый срок ресурса
     записываются **одной транзакцией**;
   - 503, таймаут, обрыв сети → результат неизвестен: задача откладывается на
     `PROVIDER_RETRY_DELAY_MS` и возвращается к шагу 1;
   - определённый отказ (4xx, в том числе 409 «ключ использован с другим телом») → «Требует внимания»;
   - три POST без подтверждения и проверка GET тоже ничего не дала → «Требует внимания».
4. Из «Требует внимания» согласующий запускает повтор. Ключ остаётся прежним, поэтому если
   операция на самом деле выполнилась, провайдер вернёт её, а не создаст вторую.

**Почему перезапуск ничего не ломает.** В памяти процесса нет ничего важного: статус заявки, задача,
число попыток и время следующего запуска лежат в базе. После запуска обработчик просто находит
задачи, которым пора выполняться.

## Защита от дублей

| Риск | Чем закрыт |
|---|---|
| Две активные заявки на один ресурс (в том числе параллельными запросами) | Частичный уникальный индекс `one_active_request_per_resource` в PostgreSQL (см. миграцию). Приложение только переводит его срабатывание в 409 |
| Два параллельных одобрения | Условное обновление `WHERE status = 'pending'` внутри транзакции: строку меняет ровно один запрос, второй получает 409 |
| Две задачи на одну заявку | Первичный ключ `dispatch_jobs.request_id` = id заявки; задача создаётся в той же транзакции, что и смена статуса |
| Потеря задачи при сбое после согласования | Та же транзакция: либо записаны и статус, и задача, либо ничего |
| Две операции у провайдера | Один стабильный ключ идемпотентности на заявку (её id); перед каждым POST — проверка GET |
| Двойной сдвиг срока | Запись результата идёт с условием `WHERE status = 'executing'`; срок записывается готовым значением из снимка, а не «+30 дней» |
| Два экземпляра приложения берут одну задачу | Захват задачи условным обновлением поля `locked_until`; захват сам истекает, если процесс упал |
| Гонки между операциями над одним ресурсом | Каждая пишущая транзакция начинается с `SELECT … FOR UPDATE` строки ресурса |

Граница гарантии: от повторного внешнего эффекта защищает идемпотентность провайдера по ключу.
Для произвольного стороннего API без такой идемпотентности это решение «ровно один раз» не обещает.

## Авторизация и доступ

- Вход по email и паролю. Пароли хранятся как хеш scrypt с солью.
- Сессия — случайный токен в cookie `sid` (`HttpOnly`, `SameSite=Lax`). В базе лежит только SHA-256
  от токена. Срок сессии — 12 часов.
- Проверка входа включена глобально для всех обработчиков; открыты только `POST /api/auth/login`
  и `GET /api/health`.
- Пользователь, его пространства и права берутся **только из базы по сессии**. Из тела запроса
  читается одно поле — `resourceId` при создании заявки. Автор, согласующий, пространство, сумма и
  даты определяются сервером.
- Нет сессии → **401**. Нет доступа к пространству или к действию → **403**, в том числе при
  обращении по известному ID чужого ресурса или заявки. Несуществующий ID → 404.

## API

Все адреса начинаются с `/api`. Тела и ответы — JSON. Ошибка: `{ "statusCode": 409, "message": "…" }`.

| Метод и путь | Назначение | Коды |
|---|---|---|
| `POST /auth/login` `{email, password}` | вход, ставит cookie | 200, 400, 401 |
| `POST /auth/logout` | выход | 204, 401 |
| `GET /auth/me` | текущий пользователь и его права | 200, 401 |
| `GET /spaces/:spaceId/resources` | ресурсы пространства с активной заявкой | 200, 401, 403 |
| `GET /spaces/:spaceId/requests` | заявки пространства | 200, 401, 403 |
| `GET /resources/:id` | ресурс, текущий срок, история его заявок | 200, 401, 403, 404 |
| `GET /requests/:id` | заявка и её история | 200, 401, 403, 404 |
| `POST /requests` `{resourceId}` | создать заявку | 201, 400, 401, 403, 404, 409 |
| `POST /requests/:id/approve` | одобрить | 200, 401, 403, 404, 409 |
| `POST /requests/:id/reject` | отклонить | 200, 401, 403, 404, 409 |
| `POST /requests/:id/retry` | повторить обработку из «Требует внимания» | 200, 401, 403, 404, 409 |
| `GET /health` | проверка, что приложение запущено | 200 |

Заявка в ответе:

```json
{
  "id": "342dece9-…", "operationKey": "342dece9-…",
  "resourceId": "res-a-01", "resourceName": "Хранилище A",
  "status": "executing",
  "createdBy": { "id": "…", "name": "Инициатор Alpha" },
  "decidedBy": { "id": "…", "name": "Согласующий Alpha" },
  "amountMinor": 128000, "currency": "RUB",
  "oldExpiresOn": "2027-03-01", "newExpiresOn": "2027-03-31",
  "providerOperationId": null, "lastError": null, "postAttempts": 1,
  "can": { "approve": false, "reject": false, "retry": false },
  "events": [
    { "at": "…", "actor": "Инициатор Alpha", "fromStatus": null, "toStatus": "pending", "note": "Заявка создана" }
  ]
}
```

Суммы — целое число копеек. Сроки — строки `YYYY-MM-DD` (в базе тип `DATE`), без времени и часового пояса.
Поле `can` — подсказка интерфейсу, какие кнопки показать; сервер проверяет права независимо от него.

## Тесты

```bash
cd backend
npm test
```

Нужна запущенная база (`docker compose up -d --wait`); тесты работают с отдельной базой
`renewals_test`, которую контейнер создаёт при первом запуске, и сами применяют к ней миграции.
Имитатор для тестов не нужен: его поведение повторяет `test/provider-stub.ts`.

Тесты идут через настоящий HTTP API и настоящий PostgreSQL и проверяют:

- 401 без входа, с испорченной и просроченной cookie; вход и выход;
- изоляцию пространств в обе стороны (Beta → Alpha и Alpha → Beta) по каждому адресу, включая
  известный ID; подстановку роли в тело запроса;
- создание заявки, снимок, запрет второй активной заявки, параллельное создание, срабатывание индекса базы;
- запрет согласования своей заявки; повторное и параллельное согласование; одновременные одобрение
  и отклонение; отклонение;
- отказ в согласовании, если срок или стоимость ресурса изменились;
- контрольный сценарий: 503 → перезапуск приложения → тот же ключ → завершено, срок сдвинут один раз;
- остановку сразу после отправки POST: попытка учтена, пауза сохранена, второго POST нет;
- три POST без подтверждения → «Требует внимания» → повтор; случай «операция выполнена, все ответы потеряны»;
- задачу, занятую другим обработчиком, и её подбор после истечения захвата;
- несовпадение операции провайдера с заявкой;
- содержимое истории.

`node scripts/acceptance.mjs` дополнительно проверяет тот же сценарий на настоящем имитаторе с
жёсткой остановкой процесса.

## Интерфейс

- Список заявок и список ресурсов пространства, создание заявки, окно заявки с действиями и историей,
  окно ресурса с историей его заявок.
- Состояния: загрузка, пустой список, ошибка с кнопкой повтора, ошибка действия (например 409).
- Данные обновляются раз в 3 секунды, поэтому переход «Выполняется → Завершена» виден без перезагрузки.
- Клавиатура: все действия — обычные кнопки и поля, окна — встроенный `<dialog>` (фокус внутри окна,
  закрытие по `Esc`), фокус виден.
- На ширине до 640px таблицы превращаются в карточки; горизонтальной прокрутки нет.

## Принятые решения и компромиссы

- **Обработчик внутри приложения и опрос базы раз в секунду** вместо брокера сообщений. Для одного
  процесса и небольшого потока этого достаточно; брокер по условию не требуется.
- **Сначала GET, потом POST.** Лишний запрос на каждую отправку, зато после любого сбоя обработчик
  сначала узнаёт правду и не шлёт POST вслепую.
- **Срок записывается готовым значением из снимка**, а не прибавлением 30 дней в момент завершения.
  Повторная запись даёт тот же результат.
- **Блокировка строки ресурса** в каждой пишущей транзакции. Операции над одним ресурсом идут по
  очереди; на разных ресурсах друг другу не мешают.
- **Частичный индекс описан вручную в SQL миграции**: Prisma не умеет выражать его в `schema.prisma`.
  Следствие: новые миграции нужно проверять, чтобы Prisma не предложила удалить этот индекс.
- **403, а не 404, для чужих данных** — так требует задание. Это раскрывает факт существования ID;
  в боевой системе я бы обсудил замену на 404.
- **Повтор из «Требует внимания» доступен любому согласующему пространства**, включая автора заявки:
  это не решение по заявке, а повтор уже согласованной операции.
- **Устаревшая заявка** (ресурс изменился после создания) остаётся «на согласовании» и получает 409
  при одобрении. Освободить ресурс можно, отклонив её.

## Ограничения и незавершённое

- **Счёт попыток — «не больше трёх POST».** Попытка записывается до отправки, поэтому если процесс
  остановят между записью и самим запросом, реальных POST окажется меньше трёх. Ошибка в безопасную
  сторону: заявка уйдёт в «Требует внимания» раньше, повтор её восстановит.
- **Обработчик рассчитан на один экземпляр приложения.** Захват задачи не даёт двум экземплярам взять
  её одновременно, но если захват истечёт посреди долгой обработки, «опоздавший» экземпляр может
  перезаписать счётчик попыток или время следующего запуска. Двойной сдвиг срока и вторая операция у
  провайдера при этом всё равно невозможны. Для нескольких экземпляров нужно добавить проверку
  своего захвата в каждое обновление задачи.
- **Из «Требует внимания» нет выхода, кроме повтора.** Если провайдер отвечает определённым отказом
  (4xx) или вернул операцию с другими параметрами, повтор даст тот же результат, и ресурс останется
  занят. С имитатором и начальными данными это недостижимо; в боевой системе нужно действие
  «закрыть заявку вручную» для администратора.
- Нет интерфейса для изменения срока и стоимости ресурса: проверка снимка покрыта тестом,
  который меняет ресурс напрямую в базе.
- Просроченные сессии не удаляются из базы фоновой задачей (они просто перестают действовать).
- Нет ограничения числа попыток входа.
- Cookie без флага `Secure`: приложение рассчитано на локальный запуск по HTTP.
- Интерфейс не покрыт автотестами; проверялся вручную на 1440×900 и 390px.
- Развёртывание, регистрация, SSO и уведомления не делались — по условию задания.
